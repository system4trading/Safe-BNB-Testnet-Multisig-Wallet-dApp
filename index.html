Host protocol support

The host recognizes the Safe Apps SDK message envelope (SAFE_APP_READY, SAFE_APP_REQUEST, SAFE_APP_RESPONSE) and safe-workspace/v2 messages (HELLO, GET_CONTEXT, REQUEST_TRANSACTION, REQUEST_TRANSACTIONS). Read-only context and selected EIP-1193 reads are supported. Transaction requests are staged for manual review only; no Safe transaction hash is fabricated and no signing/execution is performed.

v2 example: window.parent.postMessage({protocol:"safe-workspace/v2",type:"REQUEST_TRANSACTION",requestId:"req-1",transaction:{to:"0x…",value:"0",data:"0x",operation:0}},"*"). Replies use safe-workspace/v2 with type RESPONSE, the same requestId, and either result or error.

Custom Safe App security policy — manifest.json & HTTP headers

These are server-side templates for the custom app host, not settings that this parent HTML can enforce on a remote iframe. Apply them on usdtinrp-testnet.system4trading.com. Adjust the icon path and allowed parent origins to match your deployment.

1. Root manifest.json

Publish this at https://usdtinrp-testnet.system4trading.com/manifest.json. Ensure the referenced icon file exists and is a square SVG (at least 128×128 is recommended by Safe).

2. Nginx headers (template)

Merge into your existing server configuration; do not create duplicate conflicting CSP headers. Keep only parent origins you intentionally trust. The frame-ancestors directive must be an HTTP response header, not a meta tag.

3. Deployment checks

  • GET /manifest.json returns HTTP 200, JSON content type, and the CORS headers above.
  • The icon path in the manifest resolves to a publicly accessible image.
  • The app HTML response allows only the intended embedding origins via Content-Security-Policy: frame-ancestors.
  • Remove conflicting X-Frame-Options: DENY or SAMEORIGIN if cross-origin embedding is intended; do not use a wildcard frame policy just to bypass errors.
  • Open the app in the actual Safe interface and confirm the Safe Apps SDK initializes. CORS/CSP alone do not provide Safe wallet context.

Copy a template, apply it to the app server, then verify the live response headers in browser DevTools → Network.

Signature verification & execution

Cryptographic checks use the connected wallet, ethers.js and Safe contract view methods. Network access to the ethers CDN is required.
No package loaded.
Security gate closed. No signatures are trusted until the Safe hash, current nonce, owner set, threshold, and each signature are verified.

JSON fields and signature counts are never authorization. Before execution, this workspace recomputes the Safe EIP-712 hash, compares it with the Safe contract’s own getTransactionHash result, recovers each EOA signer, rejects duplicate/non-owner signatures, sorts signatures by owner address, and rechecks nonce/threshold. Contract-based owners (EIP-1271), non-standard Safe versions and batch transactions are not supported by this minimal adapter and will be rejected or remain unverified.
